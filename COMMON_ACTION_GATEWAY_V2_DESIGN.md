# CommonActionGateway V2 Design

Status: implementation design frozen before V2 source changes. The preserved V1 result remains
`TIMING_NO_GO`; V2 development must not overwrite or reinterpret it.

## 1. Security boundary

The Agent Cloud observes the long-lived Cloud-to-Gateway transport: endpoint, connection lifetime,
frame count/order, frame bytes, sender/receiver timing, and coarse public session configuration.
The trusted CommonActionGateway consists of a timing-isolated Pacer process and a separate Worker
process. Downstream provider endpoints, request plaintext, result plaintext, shared-memory rings,
and worker diagnostics are private in this experiment. Provider emulators are local processes.

For a public profile `Gamma=(B, Delta_req, Delta_resp, H, delta_mask)`, the V2 target is one
fixed-size encrypted request and response frame in every slot of a fixed public session. V2 does
not claim packet-level, microarchitectural, global traffic-analysis, or Windows scheduler privacy.

## 2. Architecture

```text
Agent Cloud process
  fixed request clock + fixed encrypted frames
            |
            | one persistent TCP tunnel for the full public session
            v
Gateway Pacer process (dedicated timing authority)
  request reader -> fixed request SPSC shared-memory ring
  response clock -> cutoff snapshot -> fixed-buffer AEAD -> public deadline write
            ^
            | fixed result SPSC shared-memory ring; polled only at public cutoffs
            |
Gateway Worker process
  decrypt -> ProviderAdapter -> idempotent effect -> fixed result record
            |
            | real local HTTP I/O
            v
Local provider-emulator processes (FAST/MEDIUM/SLOW/VERY_SLOW/JITTERED)
```

The Pacer owns the only Agent-Cloud socket. The Worker cannot access that socket and has no
callback, event, condition variable, or eventfd into the Pacer. Provider completion can mutate
only Worker-private state and the producer side of the result ring.

## 3. Literature-derived mapping

The design applies the engineering principles named in the task without copying source:

| Principle | V2 realization |
|---|---|
| Pacer: secret-independent transmit schedule | Response deadlines are generated from public `t0 + k*Delta_resp`, not from request or completion time |
| Pacer: isolate application computation | Worker/provider execution is in different OS processes; Linux affinity keeps them off the Pacer CPU |
| Pacer: mask preparation delay | Queue snapshot, RESULT/WAIT selection, fixed serialization, and AEAD finish at `Tk-delta_mask`; only wait/write remains at `Tk` |
| NetShaper: gateway/middlebox and buffering | Long-lived common tunnel plus fixed request/result shared-memory rings between Pacer and Worker |
| NetShaper: process/core separation | Pacer, Worker, Cloud client, and each provider emulator are distinct processes with diagnostic affinity status |
| BuFLO/Tamaraw-style cover | Every public slot carries one `B`-byte request and response frame; absent data becomes NOOP/WAIT |

Transport-control packets generated by TCP are not independently fixed-rate. The TCP backend is
therefore evaluated at the socket boundary only. A transport interface reserves a future
timed-datagram backend; `SO_TXTIME`/ETF is not claimed for TCP or on an unconfigured host.

## 4. Public schedule and continuation semantics

The Pacer chooses a public epoch start during connection setup. For response slot `k`:

```text
prepare_k = T0 + k*Delta_resp - delta_mask
send_k    = T0 + k*Delta_resp
```

At `prepare_k`, the Pacer performs exactly one nonblocking result-ring snapshot. If one committed
record exists, it copies the fixed record into a preallocated RESULT plaintext; otherwise it uses
a preallocated WAIT plaintext. Both traverse the same fixed-buffer AEAD routine. At `send_k`, the
Pacer only performs an absolute wait, one fixed-frame socket write, and a write into a preallocated
diagnostic ring.

The explicit continuation rule is:

> If work is not complete at a public cutoff, it remains in Worker/result state and is considered
> at the next already-scheduled cutoff.

Slow work never creates a slot. Every development session uses exactly public `H` slots. A result
still absent after slot `H` is fail-closed and remains private/undelivered; the connection is not
secret-dependently extended. A session may be followed by another public session on the same
tunnel.

## 5. Shared-memory rings

Two bounded file-backed memory mappings are used as volatile shared memory:

- request ring: one Pacer producer, one Worker consumer, fixed encrypted request records;
- result ring: one Worker ring-writer producer, one Pacer consumer, fixed result records.

The header contains aligned atomic read/write sequence counters. Records are fixed width. The
result record contains a fixed operation identifier, status, payload length, and padded payload.
Worker provider goroutines submit completions to a Worker-internal channel; exactly one ring-writer
goroutine publishes them. Publication never signals the Pacer. The Pacer polls once per cutoff.

The rings are bounded. A full request ring is a public/session failure. A full result ring is a
private fail-closed error recorded by the Worker; it cannot change the public schedule.

## 6. Provider and effect semantics

`ProviderAdapter` accepts a private fixed operation and returns a fixed result record.

- `LocalProviderAdapter` performs real HTTP request/response I/O to configured loopback provider
  emulators.
- `GenericHTTPProviderAdapter` is disabled unless explicitly enabled and is not used by timing
  development.

Provider emulators implement real HTTP servers and delay responses in their own processes. The
Worker does not emulate downstream latency with `time.Sleep`. NOOP is discarded before provider
routing and creates no effect or result record. Success, error, timeout, cancellation, and
ambiguous effect state all map to the same fixed internal result format.

Provider behavior is explicitly declared as `READ_ONLY`, `IDEMPOTENT_EFFECT`, or
`NON_IDEMPOTENT_EFFECT`. Before dispatch, the Worker durably records `PREPARED` in a local
copy-on-write/fsync operation journal. A committed result is recoverable after restart. A prepared
or failed idempotent operation may be retried with the same operation ID under the provider's
contract. A prepared/ambiguous non-idempotent operation is not retried automatically and fails
closed for reconciliation. The Gateway does not claim exactly-once for providers that cannot
support idempotency or reconciliation.

## 7. Linux reference timing path

Linux is the reference platform. The Pacer supports:

- `CLOCK_MONOTONIC` absolute sleeps;
- configured CPU affinity;
- optional `SCHED_FIFO` with explicit success/failure diagnostics;
- a configured worker CPU distinct from the Pacer CPU;
- preallocated frames, nonces, and timing diagnostics;
- no JSON, file flush, stdout/stderr, provider parsing, or allocation intended at transmit time.

Normal tests do not require privileges. If affinity or real-time scheduling cannot be applied,
the diagnostic artifact records that fact. PREEMPT_RT and isolated CPUs are deployment options,
not assumed evidence. Windows retains functional timing and affinity diagnostics but cannot
produce a V2 timing-closure claim.

## 8. V1 interference inventory

The following V1 sites allow private work to interfere with actual response release:

1. `runGateway` hosts request receive/decryption, providers, result state, response pacing, AEAD,
   and logging in one Go process and one scheduler.
2. Every non-NOOP request launches an unbounded provider goroutine in that same process.
3. Provider latency is `time.Sleep` inside the Gateway process; completion wakes its scheduler.
4. Provider completion updates shared atomics and synchronously JSON-marshals/flushes a private log.
5. The response goroutine calls `encryptResponse` only after the transmit wait; JSON formatting,
   allocation, nonce acquisition, and AEAD are therefore on the release path.
6. `randReader` opens `/dev/urandom` per response on Linux or invokes runtime randomness on Windows.
7. Response jobs are enqueued only after request read, decryption, state mutation, and synchronous
   logging, so secret-dependent work can make a public deadline late.
8. Pacer and Worker share `sync.Map`, atomic state, Go GC, heap, CPU quota, and cache hierarchy.
9. Host and private log writers marshal and flush on every event in timing-sensitive goroutines.
10. The Cloud request pacer also synchronously marshals/flushes after each send while sharing a
    process with its socket receiver.
11. V1 records a nominal response deadline supplied through each request rather than maintaining
    a wholly independent Gateway response schedule.
12. No CPU affinity, real-time policy, preparation cutoff, or isolation diagnostic is enforced.

This inventory explains the frozen Tool-frequency failure and defines the V2 implementation
acceptance tests.

## 9. Development and confirmation discipline

V2 first runs only development stress on new `results_gateway_v2/development_*` artifacts. It
reports scheduled send, actual socket send/receive, release slip, p50/p95/p99/max, and
label-conditioned distributions under private CPU/completion load. The development result cannot
be `TIMING_GO`.

After source, OS, affinity, real-time status, `delta_mask`, `B`, cadence, `H`, features,
aggregation, and equivalence margin are frozen, a separately requested run must generate an
entirely new untouched confirmatory holdout. The failed V1 `confirmatory_final_*` traces remain
immutable and are never reused to select V2 parameters.
